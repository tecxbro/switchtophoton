# Blooio source reference

## Official documentation

Reviewed 2026-11-14. Start with the [documentation](https://docs.blooio.com/), [v4 LLM index](https://docs.blooio.com/llms.txt), and [v4 OpenAPI](https://docs.blooio.com/openapi.json). Compare active legacy usage against the [v2/v4 reference](https://docs.blooio.com/reference), [v2-to-v4 comparison](https://docs.blooio.com/migrating-to-v4), and [versioned webhook guide](https://docs.blooio.com/webhooks).

## Detection

- Look for `api.blooio.com`, bearer authentication, `BLOOIO_*` configuration names, and exact locked package or generated-client metadata. v2 uses `/v2/api/chats/{chatId}/messages` with a URL-encoded chat address. v4 uses `/v4/messages` with `to` and optional sender selection via `from`. Document v3 enterprise routes separately when found and use matching repository evidence for behavior absent from the current public reference. [Documentation](https://docs.blooio.com/), [v2-to-v4 comparison](https://docs.blooio.com/migrating-to-v4)
- Detect the webhook contract independently. v2 subscription deliveries use a flat body with fields such as `event`, `message_id`, and `chat_id`. v4 uses an event envelope with `id`, `type`, `data`, and a subscription payload version in `api_version` and `X-Blooio-Version`. Confirm the running subscription version and any mixed handlers from fixtures or configuration. [Versioned webhook guide](https://docs.blooio.com/webhooks)

## Behavior to inventory

- Identify channel-specific or priority-based routing, sender channels and line eligibility, chat and contact identities, group participation, history pagination, and fallback. Inventory any active SMS, RCS, WhatsApp, or Apple Messages for Business alongside ordinary iMessage. [v4 OpenAPI](https://docs.blooio.com/openapi.json)
- Track request idempotency, webhook signature verification via `X-Blooio-Signature`, acknowledgment, retries, replays, and lifecycle state. The v4 envelope `id` identifies the event across retries and replays. `X-Blooio-Delivery` identifies a delivery, which changes on replay. Check subscription payload versions for field and error-code changes. [Versioned webhook guide](https://docs.blooio.com/webhooks)
- Record active attachments, reactions, replies, polls, typing, read receipts, contact operations, and line provisioning. Identify how the application correlates chat, channel, message, participant, and event IDs across persisted state.

## Map a direct inbound reply

1. Pin the active version and catalog ingress independently. v2 uses chat-addressed sends and older delivery envelopes. v4 has unified messages and subscription payload versions `2026-09-01` and `2026-10-01`. Verify the rendered version from headers and fixtures. The October version removes legacy aliases and `chat_guid` and changes how message errors are reported. If the repository uses v3 enterprise, match scoped legacy routes and stored payloads before planning. [Versioned webhooks](https://docs.blooio.com/webhooks), [v2-to-v4 comparison](https://docs.blooio.com/migrating-to-v4)
2. Verify the intended Keiki line and source number ownership. Keiki documents group replies on eligible dedicated `blooio` or `photon` lines. This documentation establishes a supported line type for groups. Confirm whether the existing Blooio account and number can be connected separately. Use one receiving and reply owner per conversation. [Keiki group chats](https://onkeiki.com/docs/cloud-agents#group-chats), [Keiki channels](https://onkeiki.com/docs/channels#imessage-lines)
3. Adapt the workflow's ingress to signed `keiki.turn`, with the line, organization and recipient rules verified. Only run reply logic on the supported channel and applicable entries in the turn. Ensure attachment and reply metadata are present when the source workflow requires them. [Keiki turn request](https://onkeiki.com/docs/external-harness#turn-request)
4. Replace approved direct reply paths through `/v2/api/chats/{chatId}/messages` or `/v4/messages` with the bound Keiki message operation. For attached content, use `/attachments` and `send_file`. A Keiki turn cannot walk a source priority list or choose an alternate sender on delivery failure. Capture the target ID and separate acceptance from delivery. [Blooio routing](https://docs.blooio.com/quickstart), [Keiki turn API](https://onkeiki.com/docs/external-harness#turn-scoped-api)

| Source field or behavior | Keiki mapping and evidence to retain |
| --- | --- |
| v2 `message_id`, `chat_id`, `external_id`, `internal_id`, `text`, `attachments` | Use verified `agentId` and `conversationId`, then `messages[].text`, `attachments` and `messageId`. In source history, `external_id` can be a contact or group, while `internal_id` is the organization number. Preserve both namespaces. |
| v4 `data.id`, `data.chat_id`, `data.channel_id`, `data.channel_address`, `data.protocol`, `data.text` | The inbound `sender` is the contact and `recipient` is the line. Keep direction, channel and actual transport distinct. Verify target metadata where application policy depends on the exact protocol, source line or sender. |
| v4 `data.reply_to_message_id`, attachment URL and media type | Resolve approved native operations through target-scoped IDs and documented attachment downloads. Verify multipart ordering and caption behavior before normalizing. |
| v4 envelope `id`, `X-Blooio-Delivery`, and `api_version` | `id` remains stable across retries/replays; a replay changes delivery ID. Use authenticated `turnId` and send idempotency for new target work. Preserve previous event IDs for investigation of pre-cutover retries. Verify the new app runs without consuming Blooio events. |

## Determine how much can move

- **Full for the active iMessage conversation scope, conditional until verified.** Direct replies, supported media and native actions, plus addressed replies in existing groups on eligible dedicated lines, can move when the receiving line, contact and group handling match. Check real source usage of voice, polls, effects and interactive content against the Keiki line and selected runtime. [Keiki line capability matrix](https://onkeiki.com/docs/channels#what-each-channel-supports)
- **Account for the whole gateway before removal.** Inventory channel priorities, per-send `from` selection, unified events, v4 retries and replays, group administration and any independent SMS, RCS, WhatsApp, voice or contacts. List unsupported behavior and obtain approval before dropping it. An unresolved dependency blocks Blooio retirement. Free-text reply via the same iMessage line's SMS/RCS fallback has a narrower action set and is a separate test from RCS rich-card and WhatsApp interactive processing. [Blooio v4 OpenAPI](https://docs.blooio.com/openapi.json), [Keiki channel matrix](https://onkeiki.com/docs/channels#what-each-channel-supports)
- **Blocked when the required behavior is outside the selected turn or channel.** Required first-contact or group creation, old-number continuity and raw feed parity need additional evidence. Blooio Apple Messages for Business needs its own cutover. Keiki documents an assigned, customer-initiated business channel with text/media, choices and times. Existing business ID continuity and Blooio sign-in, native Apple Pay, or other interactive payload parity are unresolved. [Blooio Apple Messages for Business](https://docs.blooio.com/guides/apple-messages-for-business), [Keiki Apple Messages for Business](https://onkeiki.com/docs/apple-messages-for-business)

## Cutover and acceptance

Capture old line/channel/priority, chat and group IDs, contact identity, subscription version and event checkpoint. Drain or reconcile queued sends according to their original sender and idempotency requests. After reconciliation, remove Blooio subscriptions and replay jobs from the migrated deployment. Preserve historical event IDs and sanitized payloads if needed for audit.

Test one v2 and one versioned v4 direct inbound where both are active. Exercise distinct contact and own-line fields, group sender, same-event replay under a new delivery ID, wrong signature or channel, missing text with media, new unknown transport/status, and response ownership on rollback. Use the [v2 message fixtures](https://docs.blooio.com/guides/message-fields), [v4 message fixtures](https://docs.blooio.com/guides/message-fields-v4), [webhook examples](https://docs.blooio.com/webhooks), and [official Node.js walkthrough](https://docs.blooio.com/guides/send-imessage-api-nodejs) for fixture and boundary examples.
