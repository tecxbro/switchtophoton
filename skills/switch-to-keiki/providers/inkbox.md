Start with the [LLM index](https://inkbox.ai/docs/llms.txt), [iMessage guide](https://inkbox.ai/docs/capabilities/imessage), [iMessage API Markdown](https://inkbox.ai/docs/api/imessage.md), [send and thread reference](https://inkbox.ai/docs/api/imessage/messages.md), and [iMessage webhook Markdown](https://inkbox.ai/docs/api/imessage/webhooks.md). ## Detection

- Look for `inkbox.ai/api/v1/imessage`, `X-API-Key`, `INKBOX_API_KEY`, and active calls such as `sendIMessage`, `send_imessage`, or `imessages.send`. Record the locked version of `@inkbox/sdk`, `inkbox` (Python or Rust), or `@inkbox/cli`. Look for `inkbox_imessage_send` in MCP tool usage. [Setup and SDKs](https://inkbox.ai/docs/get-started/quickstart.md), [API keys](https://inkbox.ai/docs/api-keys.md), [iMessage guide](https://inkbox.ai/docs/capabilities/imessage.md)
- Confirm whether the active identity uses the standard shared router, an organization-owned shared pool, or a dedicated line. Check identity scope, `imessage_enabled`, `agent_identity_id`, `conversation_id`, and subscriptions such as `imessage.received`. Identify separate phone text and mail features on the same identity. [iMessage API](https://inkbox.ai/docs/api/imessage.md), [iMessage webhooks](https://inkbox.ai/docs/api/imessage/webhooks.md)

## Behavior to inventory

- Trace router onboarding, recipient connection or assignment expiry, first-reply limits, identity rules and opt-outs, line ownership, and 1:1 or group initiation. Standard shared service receives first. Dedicated lines can initiate eligible conversations and can receive non-phone iMessage sender addresses in 1:1 threads that are receive-only. [iMessage guide](https://inkbox.ai/docs/capabilities/imessage.md)
- Preserve the distinction between `conversation_id`, message ID, and a native reply's `thread_id`. Check active `reply_to_message_id` and `plain_reply_fallback` behavior, dedicated-line groups and asynchronous group creation, and typing, read receipts, effects, tapbacks, and media flows. [Send and thread reference](https://inkbox.ai/docs/api/imessage/messages.md)
- Record the queued acceptance response separately from final delivery. Inspect `Idempotency-Key` and `Prefer: idempotency-replay` usage, polling for failures outside webhook coverage, per-identity signature verification, optional subscription authentication, and stable event `id` across retries and replays. [Send reference](https://inkbox.ai/docs/api/imessage/messages.md), [webhook guide](https://inkbox.ai/docs/webhooks.md)

## Map a direct inbound reply

1. Identify the source account and identity scope for each `imessage.received` subscription. Standard shared service waits for the recipient to connect. The organization-owned shared pool can submit an opening message as part of `/connect`, and dedicated service can start eligible chats. Inspect sender access, connection expiry and auto-shared profile behavior as well as the base API. [Inkbox iMessage guide](https://inkbox.ai/docs/capabilities/imessage.md), [Connection contract](https://inkbox.ai/docs/api/imessage/connections.md)
2. Choose an eligible dedicated Keiki line or an inbound shared number with a join code. Confirm whether a changed sender number, re-onboarding or separate Keiki contact is acceptable for the active product flow. Original Inkbox number import, router command migration and assignment continuity require evidence for the actual setup. [Keiki iMessage lines](https://onkeiki.com/docs/channels#imessage-lines)
3. Verify and queue Keiki turns before dispatching to the existing agent. Preserve the original identity-level access checks and any receive-only rules. Inbound provider events can carry permission-filtered contacts, matched identities, and optional source conversation context. Map only the fields the application consumes, with an explicit access check before passing retained contact data to the agent. [Inkbox webhook envelope](https://inkbox.ai/docs/api/imessage/webhooks.md#payload-envelope), [Keiki turn request](https://onkeiki.com/docs/external-harness#turn-request)
4. Replace approved sends from an active Inkbox conversation with the bound Keiki turn send. Use its scoped message ID for native threading and choose explicit handling for cases where the source permits an ordinary fallback. Keep the same logical idempotency key for retries, and settle the turn after side effects. [Inkbox send and thread reference](https://inkbox.ai/docs/api/imessage/messages.md), [Keiki turn API](https://onkeiki.com/docs/external-harness#turn-scoped-api)

| Source field or behavior | Keiki mapping and evidence to retain |
| --- | --- |
| `data.message.content`, `media`, and `direction` | Read inbound `messages[].text`, `content` and `attachments`. Preserve handling for media-only input, MIME checks and current-turn download lifetime. Keep outbound lifecycle callbacks outside the reply ingress. |
| `agent_identity_id`, `conversation_id`, `assignment_id`, and `remote_number` | Resolve the Keiki `agentId` and `conversationId` through a verified tenant and line mapping. Preserve the contact address type, any approved router re-onboarding and separate legacy ID lookup. Dedicated non-phone ingress is receive-only on Inkbox and needs the same suppression behavior if active. |
| `data.message.id`, `reply_to_message_id`, `thread_id`, and `plain_reply_fallback` | Use Keiki-scoped `messageId` or `replyTo.messageId` where present. Provide a separately approved ordinary send only when it reflects the active fallback behavior. A native reply on SMS/RCS fallback is unsupported by the Keiki channel matrix. |
| Source event `id`, `Idempotency-Key` and `Prefer: idempotency-replay` | Deduplicate incoming Keiki turn work by `turnId` and its side effects by deterministic keys. Compare queued source results, polling, and later status evidence with the target delivery lifecycle before changing the application's state machine. |

## Determine how much can move

- **Full for an active inbound-first 1:1 workflow, conditional until verified.** Keep the response handler and media processing on an eligible line with an approved onboarding transition. Verify which approval, rules and trusted identity metadata the source provides and how the new turn will preserve them. [Inkbox iMessage guide](https://inkbox.ai/docs/capabilities/imessage.md), [Keiki channels](https://onkeiki.com/docs/channels)
- **Resolve shared identity dependencies.** Inventory active phone/SMS, mail, calling, assignment management, permission-filtered webhook data, thread cursor reads and delivery polling. Find a replacement or obtain explicit approval for each loss before removing Inkbox. Document the special case of `send_outcome_ambiguous`, for which a retry as a new message can duplicate delivery. [Inkbox webhook guide](https://inkbox.ai/docs/webhooks.md), [Inkbox message contract](https://inkbox.ai/docs/api/imessage/messages.md)
- **Blocked for exact first-contact or group creation through the reviewed Keiki turn API.** Keiki notices need an existing conversation. Keiki can accept an addressed event in an existing group on an eligible dedicated Photon/Blooio line. Source dedicated groups support creation through `to` with 2–8 E.164 recipients and asynchronous group readiness. Required source assignments, router opening message, group creation, old thread identifiers, or non-phone inbound and its suppression need product or API evidence. [Inkbox group API](https://inkbox.ai/docs/api/imessage/groups.md), [Keiki groups](https://onkeiki.com/docs/cloud-agents#group-chats), [Keiki notices](https://onkeiki.com/docs/agent-api#notices-from-your-server)

## Cutover and acceptance

Record the old identity, recipient address, router assignment and conversation IDs, contact blocks, expiry and pending sends. Track each cohort switching to the new line or join flow. Preserve original history references and make only one runtime responsible for each inbound reply. Unregister Inkbox callbacks, remove app credentials and retire its polling jobs as part of the approved cutover.

Test active, released and expired shared assignments, dedicated phone and non-phone senders, group vs 1:1, first or repeated recipient reply requirement, permission-filtered contacts, a duplicate event, a duplicate target turn, and a queued send with an ambiguous later outcome. Include native thread, fallback, and media-only cases where needed. The [official webhook fixtures](https://inkbox.ai/docs/api/imessage/webhooks.md) and [reviewed upstream iMessage command tests](https://github.com/inkbox-ai/inkbox/blob/07b89c0b23da6e81ead290eca058762ee736ad04/cli/tests/imessage-command.test.mjs) supply source shapes. The [sender address tests](https://github.com/inkbox-ai/inkbox/blob/07b89c0b23da6e81ead290eca058762ee736ad04/cli/tests/imessage-sender-addresses.test.mjs) exercise non-E.164 handling.
