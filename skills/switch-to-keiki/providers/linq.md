# Linq source reference

## Official documentation

Reviewed 2026-11-14. Start with the [LLM index](https://docs.linqapp.com/llms.txt) or the [full iMessage documentation](https://docs.linqapp.com/channel/imessage/llms-full.txt). Match the application's generation using the [iMessage guides](https://docs.linqapp.com/channel/imessage/), [V2 reference](https://docs.linqapp.com/channel/imessage/v2/), [V2-to-V3 comparison](https://docs.linqapp.com/channel/imessage/guides/resources/migration-v2-to-v3/), and [V3 webhook guide](https://docs.linqapp.com/channel/imessage/guides/webhooks/).

## Detection

- Look for `api.linqapp.com`, the locked SDK version and imported client, and any active Vercel Chat SDK adapter. V3 SDK examples include `@linqapp/sdk`, `linq-python`, and `github.com/linq-team/linq-go`. [Client SDKs](https://docs.linqapp.com/channel/imessage/getting-started/sdks/)
- V2 signals include `/api/partner/v2`, `X-LINQ-INTEGRATION-TOKEN`, integer chat IDs, flat `chat_messages` routes, top-level `text` and `attachments`, and synchronous response assumptions. V3 signals include `/api/partner/v3`, bearer authentication, UUID chat IDs, nested chat message routes, typed `message.parts`, attachment IDs, and asynchronous delivery events. [V2-to-V3 comparison](https://docs.linqapp.com/channel/imessage/guides/resources/migration-v2-to-v3/)
- Determine the REST and webhook generations independently from active entry points, subscriptions, persisted identifiers, and fixtures. Record mixed use per endpoint or event. In V3, legacy `X-Webhook-*` headers can coexist with Standard Webhooks headers. [V3 webhook guide](https://docs.linqapp.com/channel/imessage/guides/webhooks/)

## Behavior to inventory

- Record active direct and group chat creation, participant lookup, sender line selection, recipient filtering, and automatic or explicit iMessage, RCS, and SMS selection. Include handling of phone and Apple Account email identifiers where used.
- Trace synchronous application state transitions, queued or asynchronous statuses, failure handling, `trace_id` correlation, send idempotency, and webhook acknowledgment, signature verification, retries, and deduplication using `event_id` where applicable.
- Follow attachment URLs or presigned upload sequencing, `attachment_id` usage, MIME and size restrictions, readiness, and retrieval. Inventory reply threads, read state, typing, group lifecycle, edit and unsend, voice memos, links, and other content only where the application uses them.
- Check add and remove semantics for each reachable standard reaction (love, like, dislike, laugh, emphasize, question), representative custom emoji, and each active effect. Record open-ended conversion rules and invalid values. Preserve the distinction between deleting a provider record and retracting a delivered message.
- Track persisted V2 and V3 IDs, chat history, line assignments, and active onboarding or session state through cutover. Linq's own migration endpoint maps its V2 IDs to its V3 IDs. Treat each Linq identifier as provider-specific when evaluating Keiki continuity. Inventory other Linq dependencies such as contacts or payments before retiring shared credentials or configuration.

## Map a direct inbound reply

Trace native payload combinations in addition to individual features. V3 can use `text_decorations` and `inline_stickers` with UTF-16 ranges and target a specific multipart `part_index`. Inspect calls that combine `reply_to` with `effect` or media with `effect` on one send. Keiki's raw text route rejects a combined reply and effect, and its file action has no documented effect input. Also distinguish native Name and Photo Sharing from a saveable VCF or a Keiki per-conversation contact card. See [Linq sending](https://docs.linqapp.com/channel/imessage/guides/messaging/sending-messages/), [Linq contact identity](https://docs.linqapp.com/channel/imessage/guides/chats/share-contact-card/), and the [Keiki capability matrix](../imessage-capabilities.md).

Compare effect values at the actual serializer and tool schema. For example, Linq's published demo exposes `invisible_ink` in a tool schema, while the current V3 endpoint reference lists `invisible`. Record whether the app normalizes the value, a fixture observes the provider accepting it, or the active behavior is unresolved. Map from observed source behavior before choosing a target value. [Pinned demo tool schema](https://github.com/linq-team/ai-agent-example/blob/1326d04cd9bd15dde05216bbf689f2d11b42803f/src/claude/client.ts#L238-L254), [Linq V3 send reference](https://docs.linqapp.com/channel/imessage/api/resources/chats/subresources/messages/methods/send/)

1. Capture a redacted inbound fixture and the corresponding outbound request from each live code path. Record `api_version`, `webhook_version` where present, the account and receiving line, and which event starts work. For V2, verify the optional raw-body signature used by the actual subscription. For V3, identify whether the handler verifies Standard Webhooks or the older `X-Webhook-*` format. `event_id` deduplicates provider events independently of the message ID. [V2 webhook reference](https://docs.linqapp.com/channel/imessage/v2/api/operations/webhooksevents/), [V3 webhooks](https://docs.linqapp.com/channel/imessage/guides/webhooks/)
2. Bind the intended Keiki agent to the eligible Linq line. Keiki documents Linq import. Verify the receiving number, account ownership, any line allowlist and conversation continuity for that exact line. An older `recipient_phone` field can be null even when the recipient handle is present. Use the binding and the selected Keiki envelope contract to prove source-line filtering. [Keiki setup](https://onkeiki.com/blog/how-to-add-imessage-to-your-ai-agent), [Linq webhook event types](https://docs.linqapp.com/channel/imessage/guides/webhooks/events/)
3. Preserve the application's workflow and replace its Linq ingress with a verified `keiki.turn` handler. Keep the meaning of sender/tenant authorization, media and any conversation keys. Process every applicable entry in the turn's `messages`, since Linq's individual events can be grouped into one turn. [Keiki turn request](https://onkeiki.com/docs/external-harness#turn-request)
4. Replace an approved reply on V2 `POST /api/partner/v2/chat_messages` or V3 `POST /api/partner/v3/chats/{chatId}/messages` with `POST {turnUrl}/messages` and a stable per-effect `idempotencyKey`. A threaded reply uses the Keiki message ID from the active turn. Settle the turn after required actions. Use the Keiki built-in for supported Tapbacks and list any unavailable sticker or combined payload for removal. [V2-to-V3 comparison](https://docs.linqapp.com/channel/imessage/guides/resources/migration-v2-to-v3/), [Keiki turn API](https://onkeiki.com/docs/external-harness#turn-scoped-api)

| Source field or behavior | Keiki mapping and evidence to retain |
| --- | --- |
| V2 `data.text`, `data.attachments`, `data.id`, `data.chat_id` and `data.from_phone` | Read `messages[].text` and `messages[].attachments`. Use `messageId` for a native operation and `agentId` plus `conversationId` for the new context. Keep old message/chat and customer references separately. |
| V3 `2025-01-01` `data.message.parts` and `data.message.id`, versus `2026-02-03` `data.parts` and `data.id` | Decode the actual source shape for baseline fixtures. Preserve the text/media semantics in `messages[]`. Keep structured parts or source metadata if active callers depend on their order, rich styling, or per-part target. |
| V3 `data.chat_id`, `data.from`, `data.recipient_handle.handle` versus `data.chat.id`, `data.sender_handle.handle`, `data.chat.owner_handle.handle` | Validate the target agent and line binding and resolve the application's contact from confirmed metadata. Keep Apple Account handles as opaque addresses. Recipient- or device-dependent behavior needs a documented Keiki identity field or equivalent. |
| Linq `event_id`, `trace_id`, external message status and idempotency | Use verified `turnId` for dispatch deduplication and stable send keys for side effects. Grouped turns are a different boundary from individual events. Map each active read/delivery/failure state separately and keep pre-cutover Linq trace IDs as historical data when needed. |

## Determine how much can move

- **Full for the active scope, conditional until verified.** An inbound direct text and reply bot can move when line binding, sender eligibility, routing, response semantics and every active native action match. Standard or on-request lines have different file, edit, unsend, voice and card support. A text and URL send may need separate upload and text operations. The turn API makes threaded reply and effect mutually exclusive. [Keiki line types](https://onkeiki.com/docs/channels#imessage-line-types), [Keiki turn API](https://onkeiki.com/docs/external-harness#turn-scoped-api)
- **Resolve other active Linq paths before cutover.** Map group handling, history and contact dependencies and raw event or status consumers. List any removed behavior. Disable the old reply route before Keiki takes ownership of an imported or new line. Linq V3 currently deprecates `preferred_service`; verify any old explicit choice or service-specific policy in code and fixtures. The target SMS/RCS fallback has a narrower action set. [Linq protocol selection](https://docs.linqapp.com/channel/imessage/guides/messaging/protocol-selection/), [Keiki channel capability matrix](https://onkeiki.com/docs/channels#what-each-channel-supports)
- **Blocked for required groups on an imported Linq line.** Keiki ignores groups on `linq` lines even with Group chats enabled. Supported dedicated Photon/Blooio group intake has addressing rules and does not establish group creation, membership management, or source-group continuity. Required raw lifecycle events, first send to a new contact, sender-device data, or native per-part effect/reply combinations remain unresolved until the exact target contract proves them. [Linq groups](https://docs.linqapp.com/channel/imessage/guides/chats/group-chats/), [Keiki groups](https://onkeiki.com/docs/cloud-agents#group-chats), [Keiki notices](https://onkeiki.com/docs/agent-api#notices-from-your-server)

## Cutover and acceptance

Keep a map of application tenant, source line, source chat/message reference and Keiki agent/conversation. Linq's V2-to-V3 chat migration endpoint maps Linq IDs within Linq. During an approved cutover, record the last accepted source event and drain pending replies. Remove the Linq SDK or REST client, app credentials, subscriptions and fallback after handoff. Verify one reply owner and rehearse restoring the prior deployment without replay. Check contact opt-outs before replaying any pending work.

Run fixtures for V2, each deployed V3 webhook version, and mixed use where applicable. Test wrong signature, wrong receiving line or agent, duplicate `event_id` and `turnId`, two texts in one turn, media-only input, opt-out, and timeout/ambiguous send. Build a separate assertion for each active tapback add/remove value, effect, and fallback protocol. Test group suppression as a required negative if moving only direct chats. The official [AI Agent example at the reviewed commit](https://github.com/linq-team/ai-agent-example/tree/1326d04cd9bd15dde05216bbf689f2d11b42803f) has V3 REST, nested webhook parsing, service and recipient filters, and text/media/threading. The [Linq Chat SDK repository at the reviewed commit](https://github.com/linq-team/linq-chat-sdk/tree/307ec77c9554c68fed2ec606891188f302b254f9) has adapter tests and a multi-provider Nitro app. Reuse sanitized fixtures and mock network operations.
