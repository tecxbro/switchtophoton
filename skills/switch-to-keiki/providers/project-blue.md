# Project Blue source reference

## Official documentation

Reviewed 2026-11-14. Start with the [documentation](https://docs.tryprojectblue.com/), [LLM index](https://docs.tryprojectblue.com/llms.txt), and [OpenAPI](https://docs.tryprojectblue.com/openapi.json). Check the [send message contract](https://docs.tryprojectblue.com/docs/send-message) and [webhook contract](https://docs.tryprojectblue.com/docs/webhooks) for lifecycle and integration details.

## Detection

- Look for `api.tryprojectblue.com`, bearer authentication, `/send-api-message`, `/send-group-message`, `/get-lines`, and `/get-messages-api`. Check `phone`, `message`, `lineId`, `mediaAttachmentUrl`, `audioAttachmentUrl`, and `idempotencyKey` in active sends. The public OpenAPI reports version `1.0.0`. Record the application's exact paths and generated client revision if present. [Send message contract](https://docs.tryprojectblue.com/docs/send-message), [OpenAPI](https://docs.tryprojectblue.com/openapi.json)
- Look for `message.inbound` and `message.outbound`, `direction`, `messageId`, `guid`, and `linePhoneNumber`. Identify dashboard, Zapier, or HubSpot webhook configuration because their payloads and controls differ. Identify MCP usage through `/api/mcp` and voice-specific `@tryprojectblue/dialer` separately. [Webhook contract](https://docs.tryprojectblue.com/docs/webhooks), [LLM index](https://docs.tryprojectblue.com/llms.txt)

## Behavior to inventory

- Trace automatic iMessage-to-SMS fallback, explicit `lineId` versus load balancing, group addresses versus phone numbers, media and voice memos, and effects, typing, or tapbacks where active. Check for automatic CRM contact creation and line, contact-card, workflow, or FaceTime dependencies.
- Record the difference between queued, done, and recipient delivery. In the documented send contract, repeating the same recipient and text within an hour can return a deduplicated result if the application did not choose a distinct idempotency key. Determine which repeated sends are intentional. [Send message contract](https://docs.tryprojectblue.com/docs/send-message)
- Dashboard webhooks attempt delivery once, with no retry or replay. Identify polling reconciliation through `/get-messages-api`, any response or disablement monitoring, and the message handle used for message lookup. Check `groupId`, `destination`, `sender`, and `participants` in fixtures before mapping group and 1:1 flows. [Webhook contract](https://docs.tryprojectblue.com/docs/webhooks), [LLM index](https://docs.tryprojectblue.com/llms.txt)

## Map a direct inbound reply

1. Identify dashboard, Zapier or HubSpot ingress, and the corresponding source send and status/reconciliation path. Capture active direction filtering and source fixture values for recipient and line. HubSpot automation messages expose `contactPhoneNumber`, `dateReceived` and CRM identifiers but lack the full group/sender fields. [Project Blue webhook contract](https://docs.tryprojectblue.com/docs/webhooks)
2. Choose the allowed Keiki line and agent, then document the old-number decision. The reviewed Keiki contract documents eligible lines and some provider imports. It does not establish Project Blue number import or equivalent load balancing. Bind the target to the correct tenant and receiving line before adapting sends. [Keiki channels](https://onkeiki.com/docs/channels#imessage-lines), [Keiki setup](https://onkeiki.com/blog/how-to-add-imessage-to-your-ai-agent)
3. Verify the signed Keiki turn and durably defer work keyed by `turnId`. Pass applicable inbound text and attachments to the existing reply workflow. Keep source CRM identity and allowed recipient checks with the application. Verify that two texts sent together, a missing source callback, and a CRM-triggered outbound event do not accidentally produce duplicate replies. [Keiki turn request](https://onkeiki.com/docs/external-harness#turn-request)
4. Replace the approved existing-conversation `/send-api-message` reply with `POST {turnUrl}/messages`. Use an explicit stable idempotency key for the logical reply instead of relying on Project Blue's default identical-body deduplication. Verify media and voice-note limits, and preserve any intentional CRM side effects through their owning application integration when required. [Project Blue send contract](https://docs.tryprojectblue.com/docs/send-message), [Keiki turn API](https://onkeiki.com/docs/external-harness#turn-scoped-api)

| Source field or behavior | Keiki mapping and evidence to retain |
| --- | --- |
| `event: message.inbound`, `direction: inbound`, and `message` | Use authenticated `messages[].text` and active turn routing. Use the original direction checks as baseline evidence. The occasional webhook payload from a send or call should never enter text reply logic. |
| `sender`, `destination`, `linePhoneNumber`, `groupId`, `participants` | Verify the actual source fixture because `destination` can carry the contact or a group chat ID. Keep source sender/line fields distinct. Bind new work by `agentId` and `conversationId` and confirmed context; do not reinterpret source identifiers as Keiki recipient addresses. |
| `messageId`, `guid`, and opaque list/read `message_handle` | Use scoped Keiki `messageId` for new replies and keep all source identifiers needed for reconciliation. Source numeric ID/GUID and `pbm_…` message handle are separate. |
| `lineId`, optional automatic CRM contact creation, `messageType`, `deduped` | Bound turns stay on the original conversation line. Verify any independent CRM side effects, exact device/transport dependence, and which source retries reused or deliberately changed the deduplication key. |

## Determine how much can move

- **Full for an active direct conversation scope, conditional until verified.** Existing inbound 1:1 reply workflows can move with a verified tenant and line, an approved contact transition, and matching text, effect, attachment, reaction, or typing behavior where active. Evaluate actual iMessage and fallback separately. [Keiki channel matrix](https://onkeiki.com/docs/channels#what-each-channel-supports)
- **Account for adjacent workflows.** Verify replacements for CRM creation, enrollment, dialing or FaceTime, history and reconciliation, and source-number selection. Obtain approval for any lost behavior before retiring Project Blue. Replacing the webhook contract changes the source's at-most-one delivery attempt, omission recovery through `/get-messages-api`, and any disablement monitoring. Keiki's turn delivery and the separately documented consent subscription have different semantics. [Project Blue webhook contract](https://docs.tryprojectblue.com/docs/webhooks), [Project Blue docs index](https://docs.tryprojectblue.com/llms.txt), [Keiki event webhooks](https://onkeiki.com/docs/webhooks)
- **Blocked for required source-style group initiation or exact fallback on the reviewed surface.** Project Blue `/send-group-message` accepts 2–32 remote recipients, resolves an existing group for the same set, falls back the entire group to SMS if any participant lacks iMessage, and resolves transport after queuing. Keiki's group rules cover eligible existing iMessage groups and do not establish these creation or fallback semantics. The notice endpoint also returns 404 when the recipient has no existing conversation. [Project Blue group send](https://docs.tryprojectblue.com/docs/send-group-message), [Keiki groups](https://onkeiki.com/docs/cloud-agents#group-chats), [Keiki notices](https://onkeiki.com/docs/agent-api#notices-from-your-server)

## Cutover and acceptance

Record old line and CRM contact IDs, last processed webhook and polling range, and pending sends including their idempotency keys. Reconcile the source polling feed across the switch and preserve its opaque handles for investigation. Remove Project Blue clients, callbacks and polling jobs after reconciliation and verify a single reply owner. Roll back by restoring the prior deployment and source receiver and routing with the recorded polling high-water mark and deduplication state.

Test dashboard inbound/outbound pair, an absent or disabled source webhook repaired by polling, a HubSpot fixture, addressed group versus distinct direct conversation, and a source duplicate in the one-hour implicit window. Add invalid Keiki signature, duplicate turn, media-only input, ambiguous send and line/tenant isolation. Use the [official webhook fixtures](https://docs.tryprojectblue.com/docs/webhooks), [message-list schema and response examples](https://api.tryprojectblue.com/llms/list-messages.md), and [OpenAPI shapes](https://docs.tryprojectblue.com/openapi.json) for reproducible fixtures.
