# Sendblue source reference

## Official documentation

Reviewed 2026-11-14. Start with the [LLM index](https://docs.sendblue.com/llms.txt), then consult the matching [documentation](https://docs.sendblue.com/), [API v2 reference](https://docs.sendblue.com/api-v2), [receive payloads](https://docs.sendblue.com/getting-started/receiving-messages), and [webhook guide](https://docs.sendblue.com/getting-started/webhooks).

## Detection

- Look for `api.sendblue.com` or `api.sendblue.co`, `sb-api-key-id`, `sb-api-secret-key`, and `SENDBLUE_*` configuration names. Find the exact locked version of the `sendblue` Node.js or Python package, or confirm the active `chat-adapter-sendblue`, `@sendblue/cli`, MCP, or raw REST integration. [LLM index](https://docs.sendblue.com/llms.txt), [Send API reference](https://docs.sendblue.com/api/resources/messages/methods/send), [client packages](https://docs.sendblue.com/getting-started/client-packages)
- Identify each active API surface. Current messaging uses `/api/send-message` and `/api/send-group-message`. Retrieval uses `/api/v2/messages`, and account webhook subscriptions use `/api/account/webhooks`. Older calls may use paths such as `/accounts/messages`. Distinguish endpoint generation from line generation because some features require V2 lines. [API v2 reference](https://docs.sendblue.com/api-v2)
- Corroborate callbacks and persisted identifiers using fields such as `message_handle`, `from_number`, `to_number`, `sendblue_number`, `is_outbound`, `service`, `was_downgraded`, `group_id`, and `reply_to`. Capture any mixed webhook or REST behavior from the application's fixtures and configuration. [Receive payloads](https://docs.sendblue.com/getting-started/receiving-messages)

## Behavior to inventory

- Record sender selection and line continuity, shared-line recipient verification, dedicated-line plan behavior, group IDs and participant changes, iMessage/SMS/RCS routing, and fallback rules. Preserve replyable Apple Account email addresses where the application handles them.
- Trace inbound and outbound webhooks and per-send `status_callback` deliveries, including overlap, signature checks, response timing, duplicates, retry handling, and delivery state transitions. Identify stored `message_handle` values that connect sends, callbacks, reactions, inline replies, history, or reconciliation.
- Inventory media URLs and their expiration, uploads, size limits, voice memos, effects, rich media, app-card sessions, typing, read receipts, tapbacks, and other rich features when used. Distinguish application deletion of a provider record from iMessage unsend. Check active opt-out state, contact rules, line provisioning, calling, and other Sendblue dependencies that share the same configuration.

## Map a direct inbound reply

Inspect the resolved adapter package as well as the application's webhook route. For example, a Chat SDK handler can delegate receive-state and service filters, mark-read, typing, message IDs, group and Apple Account routing, and plain-text formatting to the locked Sendblue adapter. Those behaviors can be invisible in the app's direct calls. A matching fixture should cover the delegated behavior that the app actually relies on. [Sendblue Chat SDK adapter](https://github.com/sendblue-api/chat-adapter-sendblue)

1. Identify the source's account `receive` webhook or account stream. For `GET /api/v2/events`, the account SSE feed is live and the application repairs disconnect gaps through list/read endpoints. For webhooks, distinguish account-level `outbound` from a send's `status_callback`. Inspect the configured signing mechanism and, for Chat SDK integrations, the adapter's allowed services and lines and its encoded thread IDs. [Account event stream](https://docs.sendblue.com/api/resources/events/methods/stream), [Sendblue Chat SDK adapter](https://github.com/sendblue-api/chat-adapter-sendblue)
2. Record the actual Sendblue `from_number`, tracked receiving number and whether automatic line selection or a verified-contact plan is involved. The generated send API describes automatic selection for eligible accounts. Verify a target Keiki line and decide what happens to the old number and contact verification since Sendblue line import or porting is unresolved in the reviewed contract. [Send API reference](https://docs.sendblue.com/api/resources/messages/methods/send), [Keiki line setup](https://onkeiki.com/docs/channels#imessage-lines)
3. Verify and queue the Keiki turn once by `turnId`. Preserve the application's allowlist, opt-out and escaping logic, and pass applicable incoming texts and media to the existing model or handler. Handle bursts and a turn carrying both text and attachments. Test Apple Account email handles independently if the app receives them. [Sendblue receive payloads](https://docs.sendblue.com/getting-started/receiving-messages), [Keiki turn request](https://onkeiki.com/docs/external-harness#turn-request)
4. Replace an approved response through `/api/send-message` with `POST {turnUrl}/messages`. Use `replyToMessageId` for a native reply if active. Upload outbound media and call `send_file` if supported by the selected line, checking voice-note behavior separately. Keep returned Keiki IDs in a separate namespace from Sendblue message handles. [Keiki turn API](https://onkeiki.com/docs/external-harness#turn-scoped-api)

| Source field or behavior | Keiki mapping and evidence to retain |
| --- | --- |
| `is_outbound: false`, `content`, `media_url` | Only inbound input should reach the reply handler. Read `messages[].text`, model-ready `content` and `attachments[]` from the filtered turn. A provider CDN URL can expire under a different policy than a turn's attachment URL. |
| `from_number` or `number`, `to_number` or `sendblue_number`, `group_id` or encoded thread ID | Bind the verified Keiki agent and line, and use `conversationId` for the new conversation. Confirm address behavior for phone-only, Apple Account email, group and multi-line cases. Never derive a Keiki identity from a Sendblue thread ID. |
| `message_handle`, `reply_to.message_handle`, `thread_originator.message_handle` | Use `messages[].messageId` or `replyTo.messageId` when present. A reply to a previously stored source handle requires a confirmed target reference. |
| `service`, `was_downgraded`, per-send status | Preserve business rules based on the actual channel/transport only if the selected Keiki contract exposes what they need. Keiki send acceptance and later delivery are different checkpoints. |

## Determine how much can move

- **Full for an active inbound-only conversational scope, conditional until verified.** Plain 1:1 replies can map on an eligible line. Verify file behavior and effects separately. Retain active native reaction or sticker flows on Sendblue, or block the dependent switch. [Current migration scope](../imessage-capabilities.md#current-migration-scope) Match the application's source service allowlist and its verified contacts or establish approved contact onboarding. Retest acceptable delays, fallback and app-visible outcomes. [Keiki channel matrix](https://onkeiki.com/docs/channels#what-each-channel-supports), [Sendblue plan and integration index](https://docs.sendblue.com/llms.txt)
- **Partial with retained raw provider behaviors.** Keep history or recovery consumers, account-line events, send callback workflows, group administration, or caller-selected sender routing when those are active and only the reply loop has a mapping. AgentKit's delivery callback is an option to verify separately. Sendblue older adapter features and raw REST can differ, including tapback removal. [Sendblue adapter](https://github.com/sendblue-api/chat-adapter-sendblue), [Sendblue reactions API](https://docs.sendblue.com/api-v2/reactions), [Keiki SDK lifecycle](https://onkeiki.com/docs/sdk#agent-lifecycle)
- **Blocked on the proposed surface when exact card or outbound behavior is essential.** Sendblue's App Card continuation reuses a session and returns a new message handle. Keiki URL cards require an eligible purchased line and verified custom domains for customer-owned IDs. A Sendblue `data:?ver=` state payload cannot be passed to Keiki's HTTPS-only card route. Existing card session/revision continuity, source number import, email-address replies and first-contact sends require separate evidence. [Sendblue App Card contract](https://docs.sendblue.com/api-v2/app-cards), [Keiki app cards](https://onkeiki.com/docs/imessage-apps), [Keiki notices](https://onkeiki.com/docs/agent-api#notices-from-your-server)

## Cutover and acceptance

Capture send handles and settled or queued statuses, verified-contact rules, suppression state, line-to-thread assignments and any account webhook shared with other senders. Move narrowly by line or tenant. Establish who owns retries for pending sends, which status subscriptions stay active, and how routing rolls back. Disable duplicate reply paths after the approved handoff while retaining unrelated callbacks.

Run fixtures for real code shapes such as inbound `receive`, `is_outbound`, duplicated webhook delivery, overlapping status callbacks, `was_downgraded`, inline reply, a second allowed or forbidden line and a multi-line sticky thread. Exercise `media_url` expiration, invalid authentication, short-lived turn credentials, and timeout with unknown send result. If App Cards or SSE are required, include continuation/revision or reconnect-and-gap-repair acceptance separately. Use the [official Sendblue Chat SDK adapter source](https://github.com/sendblue-api/chat-adapter-sendblue) for integration behavior and [official receive fixtures](https://docs.sendblue.com/getting-started/receiving-messages) for representative payloads.
