# Keiki evidence and capability verification

The references below were checked on 2026-11-14. Retrieve the contract again for the actual migration and record the date. Start from the [Keiki docs index](https://onkeiki.com/docs), [agent-readable index](https://onkeiki.com/llms.txt), and [developer portal](https://onkeiki.com/developers).

## Identify the public contract

- **Hosted service.** Record the service origin, operation or event name, supported inputs and outputs, authentication, lifecycle, and documentation date. The [Keiki Agent API OpenAPI document](https://onkeiki.com/openapi.json) describes the model gateway and selected developer endpoints. Use the [external harness guide](https://onkeiki.com/docs/external-harness) and [event webhooks guide](https://onkeiki.com/docs/webhooks) for the separately documented contracts. The OpenAPI document's version identifies that API description.
- **Installed package.** Record the exact planned version, public exports and types in the published package, matching framework/runtime requirements, and the version resolved at verification. Use the official guide alongside the pinned public package. Inspect official package implementation or tests when a discrepancy matters. Record the version or revision examined.
- **Channel.** Record the actual agent, provider and line type, transport, required configuration or addon, and evidence for the specific action. Use separate cases for direct iMessage, groups, SMS/RCS fallback, shared lines, and Apple Messages for Business when active. [Keiki channels](https://onkeiki.com/docs/channels)

The registry reported [`@onkeiki/agents@0.1.7`](https://www.npmjs.com/package/@onkeiki/agents/v/0.1.7), [`@onkeiki/channels@0.1.6`](https://www.npmjs.com/package/@onkeiki/channels/v/0.1.6), [`@onkeiki/ai-sdk@0.1.8`](https://www.npmjs.com/package/@onkeiki/ai-sdk/v/0.1.8), [`@onkeiki/flue@0.1.6`](https://www.npmjs.com/package/@onkeiki/flue/v/0.1.6) and [`@onkeiki/eve@0.1.7`](https://www.npmjs.com/package/@onkeiki/eve/v/0.1.7) at the time of review. These are observations for the reference, with package selection and pinning specific to each migration.

For example, the hosted external-harness guide documents lease refresh, return links, the `send_widget` action, and HTTP 429 `recipient_reply_required`. The published `@onkeiki/channels@0.1.6` declarations and client do not expose helpers for lease or return link, a typed `send_widget` action, or a distinct reply-required result. If one of those behaviors matters, verify the chosen version or use the documented raw HTTP contract and test its result handling. [External harness contract](https://onkeiki.com/docs/external-harness), [Published channels package metadata](https://registry.npmjs.org/@onkeiki%2Fchannels/0.1.6)

## Verify the active behavior

| Boundary | Public evidence and what to check |
| --- | --- |
| Signed inbound turns | `keiki.turn` v1 carries `turnId`, `agentId`, `conversationId`, messages, and a turn URL. Verify the raw request using the documented timestamped HMAC or platform Ed25519 signature before handling it. Validate the agent binding, acknowledge durable acceptance with 2xx, and keep the short-lived turn credential out of logs. Test invalid signatures, duplicate dispatch, held-back turns, cancellation, and the chosen mid-turn behavior. [Turn request](https://onkeiki.com/docs/external-harness#turn-request), [Mid-turn arrivals](https://onkeiki.com/docs/external-harness#mid-turn-arrivals) |
| Outbound delivery | `POST {turnUrl}/messages` uses the turn bearer. Supply a stable per-send idempotency key. `replyToMessageId` and `effect` are mutually exclusive. A duplicate successful key acknowledges without resending. After an ambiguous failure the same key can return `previous_attempt_failed` and a new key risks duplicate delivery. Handle `recipient_reply_required` without retry until a real recipient reply. Separate request acceptance from delivery observed on a device. [Turn-scoped API](https://onkeiki.com/docs/external-harness#turn-scoped-api), [Recipient reply required](https://onkeiki.com/docs/external-harness#recipient-reply-required) |
| Attachments and native operations | Verify the incoming attachment envelope and signed download URL expiry against the turn-scoped download route. For outbound upload, send bytes with the filename and MIME type and pass the returned attachment ID to `send_file`. Apply both the upload and selected channel limits. For tapbacks, edits and deletion, use Keiki's scoped `messageId` and test operation support and visible behavior. Inbound reaction events are documented for push and inbox, with different delivery semantics. [Turn-scoped API](https://onkeiki.com/docs/external-harness#turn-scoped-api), [Reaction events](https://onkeiki.com/docs/external-harness#reaction-events), [Line capabilities](https://onkeiki.com/docs/channels#imessage-line-types) |
| Completion and recovery | Finish only after applicable sends and tool calls settle. Exercise duplicate completion, cancellation, deadline, and stale-token behavior. Push apps handling arrivals acknowledge processed sequence numbers at completion. Inbox pollers need lease handling and stable idempotency keys across reclaim. Relay mode forwards claims and has different arrival and reaction behavior. [Completion and errors](https://onkeiki.com/docs/external-harness#completion-and-errors), [Relay and inbox modes](https://onkeiki.com/docs/external-harness#relay-mode) |
| Consent | `keiki.conversation.opt_status_changed` v1 is a separate signed subscription. Acknowledge after durable acceptance, deduplicate by verified `eventId`, and account for out-of-order delivery. Confirm source STOP/START semantics and suppression when migrating. Enabling the subscription does not backfill historical events. [Event webhooks](https://onkeiki.com/docs/webhooks) |
| Provisioning and line state | `POST /api/v1/developer/deployments` upserts by `external_ref` with an org-wide scoped credential. Read each channel result and verify its line binding before traffic moves. An upsert can purchase a line or return a payment requirement. Deleting a line or deployment can release the number. [Partner deployments](https://onkeiki.com/docs/partner-deployments) |

For every active behavior, document the exact source evidence, Keiki endpoint or tool with its applicable version or line, authentication and identity rules, response and failure semantics, and verification case. Enumerate reachable values of closed sets such as event types, effects, or delivery states. For open-ended values such as text, MIME types, custom reactions, and opaque IDs, document the transformation and test representative, invalid, and unknown inputs. Treat provider and Keiki IDs as opaque unless the public contracts and the migration's test cases establish a reversible mapping.

Use explicit evidence states. **Verified** means the exact public contract supports the mapping for the selected prerequisites. **Conditional** means a documented prerequisite still needs confirmation. **Unsupported** requires a public constraint that rules out the operation on the selected surface. **Unresolved** covers incomplete or conflicting evidence. Check another Keiki surface or inspect official package evidence if that can settle the uncertainty. A missing example, an unavailable source, or a type that accepts arbitrary strings cannot settle capability coverage.

Keep documentary evidence and runtime verification distinct in the plan. Run sandbox or held-back checks for handler behavior, then use a real test conversation when the approved scope includes verifying device-visible behavior. A playground reply or successful provisioning response cannot establish iMessage delivery or native action parity. [Held-back turns](https://onkeiki.com/docs/external-harness#held-back-turns), [External-channel evals](https://onkeiki.com/docs/external-channel-evals)
